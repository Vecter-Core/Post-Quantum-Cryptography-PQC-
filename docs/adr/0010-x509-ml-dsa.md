# ADR-0010: X.509 certificates with pure ML-DSA

- Status: accepted
- Date: 2026-09-29

## Context
PKI underlies TLS server and client authentication, code signing and device identity.
Signatures in long-lived certificates (roots and intermediates live 5 to 25 years) are the
tier-1 migration item of ADR-0003. The IETF has standardised ML-DSA in X.509: RFC 9881,
formerly draft-ietf-lamps-dilithium-certificates, specifies:
- the OIDs `id-ml-dsa-{44,65,87}` with absent parameters;
- the raw public key in `SubjectPublicKeyInfo`;
- pure ML-DSA with an empty context over the DER `TBSCertificate`;
- a PKCS#8 private-key CHOICE of `seed`, `expandedKey`, or `both`.

OpenSSL (3.5 and later) implements it, and so does Python `cryptography` 50 on top of OpenSSL.
Composite (hybrid) certificates are specified separately and are still settling.

## Decision
- New crate `vpqc-x509`, which provides:
  - ML-DSA-65/87 keys as SPKI and PKCS#8;
  - self-signed CAs and issued certificates (CA / intermediate / end entity, SAN DNS names,
    EKU server / client / code signing, SKI / AKI);
  - a chain verifier;
  - CLI `vpqc x509 key|ca|issue|verify`.
- **Pure ML-DSA, not composite**, for the same reason as JOSE (ADR-0008): certificates must
  validate in other stacks. Recommended profile: ML-DSA-87 for roots and long-lived
  intermediates, ML-DSA-65 for end entities.
- PKCS#8 is written in the **seed-only** form (54 bytes, as RFC 9881 recommends).
  - Reading accepts `seed` and `both`, and checks that the expanded key matches the seed.
  - `expandedKey`-only is refused: without the seed, the key can neither be checked nor
    re-exported.
- Certificates are encoded by a small DER writer in the crate, which keeps the encoding
  auditable, and parsed with x509-parser. Every certificate is parsed back and its signature
  verified before it is returned.
- `verify_chain` is deliberately small. For every certificate in the path it checks:
  - v3 format;
  - an ML-DSA signature by the next certificate, with the issuer name byte-equal to the
    issuer's subject;
  - validity at the given time;
  - no unknown critical extension.

  It also checks the CA constraints: basic constraints, key usage and path length. For the
  leaf it checks: not a CA, `digitalSignature`, EKU, and DNS name against the SAN (wildcards
  cover one label). Name constraints, policies and revocation are not implemented; chains
  that need them are rejected (critical) or unaffected (non-critical). It is not a
  replacement for a full validator such as webpki in general TLS clients.

## Consequences
- Interop is tested in CI in both directions (`interop/x509.sh`, 52 checks):
  - OpenSSL, through `cryptography`, verifies vpqc chains, including its full RFC 5280
    `PolicyBuilder` server verifier;
  - Node.js verifies vpqc chains too;
  - vpqc verifies OpenSSL-built chains and rejects bad variants: wrong name, wildcard depth,
    purpose, expiry, wrong signer, non-CA issuer, path length, tampering;
  - keys move both ways, including Node's `both` PKCS#8 form, and an inconsistent `both`
    key is rejected.
- A fuzz target covers untrusted certificates, PKCS#8 and SPKI. An injected
  "skip signature check" bug is found within seconds.
- `x509-parser` pulls `time` 0.3.55 or later (the RUSTSEC-2026-0009 fix), so this crate needs
  Rust 1.88, like `vpqc-scan`.
- ML-DSA certificates are large (measured):
  - an ML-DSA-65 end entity is about 5.6 KB if signed with ML-DSA-65, and 6.9 KB if signed
    with ML-DSA-87;
  - an ML-DSA-87 CA certificate is 7.5 KB;
  - a leaf plus an ML-DSA-87 intermediate is about 14 KB on the wire (root excluded).

  This matters for TLS handshakes and embedded devices. It is one reason why TLS in vpqc
  (`vpqc-tls`) keeps classical certificates for now while the key exchange is hybrid.
